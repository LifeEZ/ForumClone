# React Query owns the client cache; api.ts owns the transport

We adopt React Query (TanStack Query) for client-side server-state caching, loading/error state, refetch orchestration, invalidation, and transient-error retry across views and shell. The HTTP client (`lib/api.ts`) retains only the concerns that must apply to every request regardless of caller: token refresh on 401, error parsing/mapping (`ApiError`, `SessionExpiredError`), and the bearer header. Transient retry (429/5xx) moves out of `api.ts` into React Query's `retry` function — RQ already has access to attempt count and error type, and every `api.ts` call site now goes through RQ (queries, mutations, bootstrap `['me']`). The only non-RQ call is `logout` (best-effort, no retry needed) and the internal `refreshTokens` call (which should not retry on its own — if refresh hits a 5xx it fails, the original request fails with that 5xx, and RQ retries the whole original request, which re-attempts refresh transitively). An `api.ts`-level retry loop would duplicate RQ's `retry`/`retryDelay` for queries and mutations, so transport-level retry is removed. Token refresh stays in the transport (not in RQ's `onError`) because it must also fire for `loginUser` / `registerUser` mutations, which are RQ calls but go through the same code path — keeping auth recovery in one place. Token plumbing is decoupled from the React tree via a `TokenService` singleton (in-memory + localStorage) that holds the access and refresh tokens; `api.ts` reads both from `TokenService`, `AuthContext` writes them after login. Bootstrap (`fetchCurrentUser` before there is a user in React state) and refresh (`refreshTokens` inside `api.ts` 401 recovery) can't source the token from the React tree, which is why tokens live in `TokenService` rather than being passed as queryFn args. `AppContext` is deleted; the shell chrome reads the same hooks as page views, so there is one client cache, not two.

Session expiry is unified: any `SessionExpiredError` thrown from any React Query query or mutation triggers a single global `QueryCache.onError` / `MutationCache.onError` handler that calls `AuthContext.logout()` and `queryClient.clear()`. The fetch-then-401-then-refresh-then-fail-then-logout loop is broken by `queryClient.clear()` — no queries remain active to re-trigger. Bootstrap (`fetchCurrentUser` on app load) is moved out of `AuthContext`'s hand-rolled effect into `useQuery(['me'], fetchCurrentUser, { enabled: !!TokenService.hasAccessToken() })`, so session expiry during bootstrap flows through the same global handler as runtime session expiry.

**Consequences**

- A single-action 401 whose refresh fails (e.g. a vote with an expired refresh token) previously rolled back silently and left the user on the page; it now triggers the global handler and logs the user out. To preserve reddit-style optimistic UX, vote (and similar) mutations use **layered** error handling: `onMutate` applies the optimistic update, `onError` on the mutation rolls back the optimistic update, the global `MutationCache.onError` then fires `logout()` if the error is `SessionExpiredError`. So the user sees the vote briefly appear and roll back, then the app transitions to logged-out state — never "stuck on stale state with no indication."
- `frontend/CONTEXT.md` gains `Token layer` glossary terms (Access Token, Refresh Token, SessionExpiredError) to sharpen the ownership boundary.
- `staleTime` default is `0` (preserves today's always-refetch baseline); per-query overrides are explicit: home feed 30s, communities 60s, post detail 10s, comments 5s.
- Query keys are flat tuples, entity-first: `['communities']`, `['community', name]`, `['community', name, 'posts']`, `['post', postId]`, `['post', postId, 'comments']`, `['home']`, `['me']`. Invalidations live in `lib/invalidations.ts` as exported helpers (e.g. `communityMembership(qc, name)`), so adding a new dependent query means changing one map instead of every mutation's `onSuccess`.
- `QueryClientProvider` is mounted as a child of `AuthProvider` so the global error handler can read `logout()` from the auth context.
- Initial-load SSR still produces a client-rendered loading spinner (views are `'use client'` today); adding `HydrationBoundary` prefetch is a follow-up, not part of this decision.
- Transient retry moves from `api.ts`'s `fetchWithRetry` loop to React Query's `retry` (and `retryDelay` for exponential backoff). The server's `Retry-After` header on 429 responses is no longer honoured — RQ's `retryDelay` receives only `(failureCount, error)`, not the response object, so the header is lost once `api.ts` throws `ApiError(status, message)`. If honouring `Retry-After` becomes important, attach it to `ApiError` as a field and read it in `retryDelay`. For v1, plain exponential backoff is fine — the backend's 429 responses are rate-limit signalling, not server-side throttling with a precise wait window.
